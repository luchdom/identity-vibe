# Orders JSON Bulk Seed Plan (100+ Sample Orders)

Date: 2026-02-26
Status: Planned (pre-implementation)

## Goal

Add a checked-in JSON dataset to `Orders` with 100+ realistic sample orders and seed it automatically on app startup (dev/sample use), so the project has enough data for:

- dashboard widgets/charts
- list filtering/pagination demos
- order detail pages
- status history displays

## Current State (audited)

### Startup seeding path

- `src/backend/Orders/Program.cs`
  - calls `await context.Database.EnsureCreatedAsync();`
  - then `new DatabaseSeeder(context).SeedAsync();`

### Current seeder

- `src/backend/Orders/Data/DatabaseSeeder.cs`
  - seeds **2 hardcoded customers**
  - seeds **1 hardcoded sample order**
  - seeds items + one status history row
  - only seeds when tables are empty (`if (!_context.Orders.Any())`)

### Important architectural implication

`Orders` stores `Order.UserId` as the JWT `sub` claim string.

- User-specific list endpoint filters by exact `UserId`
- Admin list endpoint can see all orders

This means pre-seeded orders may **not** appear in a regular user’s `/orders` list unless the seeded `UserId` values are intentionally aligned with real AuthServer user IDs (which are generated by AuthServer and not known to Orders at seed time).

This is the main design decision to settle before implementation.

## Recommended Solution Shape

Recommended location:

Why:

- no startup randomness drift

### 2. Extend `Orders.Data.DatabaseSeeder` to import JSON dataset

Keep current seeder class, but split into explicit steps:

- seed baseline customers (or merge into JSON-driven import)
- seed from JSON file (bulk orders)
- fallback minimal sample order only if JSON disabled/missing (optional)

### 3. Use a dedicated seed JSON file only (no `appsettings` seed config)

Do not add a `SeedData` section to `appsettings*.json`.

Use a dedicated file only:

- `src/backend/Orders/Data/Seed/orders.sample.v1.json`

Seeder behavior for v1 is code-driven:

- mode = `IfEmpty` (seed only when `Orders` table is empty)
- path = fixed content-root-relative file path

### 4. Treat JSON as a sample dataset source, not a migration

Seeding should be:

- idempotent enough for startup safety
- simple enough not to become a migration system

v1 recommendation:

- If `Orders.Any()` => skip bulk import and log

## Seeder Import Logic Plan

### A. Add seed DTOs (JSON import models) in Orders backend

Recommended folder:

- `src/backend/Orders/Data/Seed/Models/*`

Models:

- `OrdersSeedDataset`
- `SeedOrder`
- `SeedCustomer`
- `SeedOrderItem`
- `SeedOrderStatusHistory`
- optional enum/string parsing helpers

Prefer:

- `sealed record` + `init` + `required`

### B. Load and validate JSON file

In `DatabaseSeeder`:

1. Resolve file path (content root relative)
2. Read JSON
3. Deserialize with `System.Text.Json`
4. Validate dataset before writing any rows:
   - at least 100 orders (or configurable minimum)
   - unique `orderNumber`
   - each order has >=1 item
   - valid status enum values
   - required customer fields present
   - numeric values non-negative where expected

If invalid:

- log clear error
- fail startup (recommended for dev/sample consistency)

### C. Import customers (dedupe by email)

Because `Customer.Email` has a unique index:

- build in-memory map by email
- reuse existing customer if found
- create new customer otherwise

Recommendation:

- do not overwrite existing customer rows on seed import in v1
- only create missing customers

### D. Import orders + items + status history

For each `SeedOrder`:

1. Create `Order` entity
2. Create `OrderItem` rows
3. Compute line totals (`CalculateLineTotal`) and order totals (`UpdateTotals`)
4. Apply timestamps/status-specific timestamps (`ShippedAt`, `DeliveredAt`, `CancelledAt`)
5. Add `OrderStatusHistory` rows

Important consistency rule:

- Seeder should calculate totals from items instead of trusting JSON totals blindly
  - optional: validate JSON totals if present and log mismatch

### E. Idempotency / startup behavior

Recommended v1 behavior:

- if `_context.Orders.Any()` => skip JSON seeding entirely
- log `"Orders already exist, skipping sample JSON import"`

This avoids duplicate/demo drift while keeping startup safe.

## Generation Strategy (how to get “random 100+” data)

Recommended v1:

- generate once (script/tool), commit the resulting JSON file

Options for generation:

- small .NET console/script in `tools/` (recommended if you want reproducibility in repo)
- one-off script (PowerShell/Python) used to generate and then deleted (faster, less maintainable)

What the generator should produce:

- 120-200 orders
- mixed statuses (`Draft`, `Confirmed`, `Processing`, `Shipped`, `Delivered`, `Cancelled`)
- date spread (last 90-180 days)
- varied item counts (1-6)
- varied categories/prices
- realistic status histories aligned with final status

## Risks / Gotchas

1. **User-specific list visibility**
- Seeded orders may not show for logged-in non-admin users if `UserId` values don’t match AuthServer user `sub`.

2. **Startup time**
- 100-200 orders is small, but large histories/items can slow startup slightly.

3. **Data drift**
- If dataset is random on every start, screenshots/tests become inconsistent.
- Prefer committed deterministic JSON.

4. **SQLite constraints**
- Unique `OrderNumber`
- Unique `Customer.Email`
- Seeder must dedupe/validate accordingly

## Recommendations (summary)

1. Commit a deterministic JSON dataset (`orders.sample.v1.json`) with 120-200 orders
2. Seed only when DB is empty (`IfEmpty`)
3. Use nested order aggregate JSON shape (customer + items + statusHistory)
4. Add seeder validation and a small test suite
5. Accept that v1 seeded data is primarily for admin/all-orders + dashboards unless you also solve user-id alignment

## Open Questions (to answer before implementation)

### Q1 (Important): Who should “own” seeded orders (`Order.UserId`)?

Because Orders filters user lists by JWT `sub`, pre-seeded orders usually won’t belong to real AuthServer users.

Options:

1. **Seed mainly for admin/all-orders dashboards** (Recommended v1)
   - Use synthetic user IDs like `seed-user-001`
   - Admin screens and dashboards show data
   - Regular user `/orders` may be empty unless they create orders

2. **Force some seeded orders to known hardcoded IDs**
   - Fragile because AuthServer user IDs are generated and can change on DB reset

3. **Add a special dev mapping strategy**
   - More complex (cross-service coupling or post-login cloning)
   - Not recommended for this sample-data task

Recommended: **Option 1**

1. **Seed only if Orders table is empty (`IfEmpty`)** (Recommended)
